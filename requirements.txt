# Fully pinned, including transitive dependencies.
#
# This file was a list of 20 bare package names until CI proved that was
# not reproducible: a developer's existing virtualenv held openai 3.3.1,
# while a clean `pip install -r requirements.txt` resolved to a newer SDK
# that raises at ChatOpenAI construction rather than at first call - so
# the suite passed locally and failed on a clean checkout. `openai` is a
# TRANSITIVE dependency (via langchain-openai) and was therefore never
# named here, which is exactly why pinning only the direct dependencies
# would not have caught it.
#
# The same reasoning applies to deployment: Render reinstalls from this
# file on every build, so an unpinned tree means an upstream release can
# change the running app with no commit of ours.
#
# The 20 packages actually chosen by this project - everything else below
# is something one of these pulled in:
#
#   langgraph, langchain, langchain-openai, langchain-community, ddgs,
#   python-dotenv, requests, beautifulsoup4, pypdf,
#   langgraph-checkpoint-postgres, psycopg[binary,pool], fastapi, uvicorn,
#   python-docx, python-multipart, pgvector, pydantic-settings, pytest,
#   pytest-asyncio, httpx
#
# Note this is NOT a raw `pip freeze`. A freeze of a working virtualenv
# also captures whatever the editor installed into it - here ipykernel,
# ipython, debugpy, pyzmq, tornado and their tails, 26 packages that would
# be reinstalled on every Render build and baked into every Docker image
# for nothing. What is pinned below is the dependency closure of the 20
# packages above, computed from installed metadata with extras and markers
# evaluated, so `psycopg[binary,pool]` keeps psycopg-binary and
# psycopg-pool while the notebook stack is left out.
#
# To add a dependency: install it, run the suite, then re-derive this list
# rather than pasting a bare `pip freeze` over it.
