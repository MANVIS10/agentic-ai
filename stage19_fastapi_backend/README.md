# Stage 19: FastAPI Backend

## What was added

Stage 18's exact multi-agent graph, wrapped in a FastAPI HTTP API instead
of a terminal REPL. Every earlier stage's entrypoint blocked on `input()`
in the same process that ran the graph; this stage swaps that for four
HTTP endpoints, so the graph and its Postgres-backed checkpoints can be
driven by any HTTP client instead of a person typing into a terminal.

Nothing about the graph itself changed — every node, edge, tool, and
prompt in `main.py` is copied verbatim from
[`stage18_postgres_persistence/main.py`](../stage18_postgres_persistence/main.py),
including its `PostgresSaver` checkpointer setup. Only what sits *around*
`graph.invoke(...)` is new.

## New concept

`interrupt()`/`Command(resume=...)` now span two separate HTTP requests
instead of one blocking REPL turn. `human_approval()` still calls
`interrupt("Approve this plan? (y/n): ")` exactly as before — but there's
no `input()` over HTTP, so the process that hits that interrupt can't just
wait for an answer. Instead:

- `POST /chat` runs the graph until it pauses at `human_approval` and
  returns the plan + approval prompt right away, ending that request.
- The human's decision arrives later, as its *own* `POST /approve` or
  `POST /reject` request, which resumes the same `thread_id` with
  `Command(resume="y"/"n")`.

The graph doesn't know or care that its caller changed — `interrupt()`
pauses execution inside a node and hands control back to whatever called
`.invoke()`, REPL loop or HTTP route handler alike. What *is* new is that
`graph.get_state(config)` — a nice-to-have debugging tool in Stage 18's
`verify_persistence.py` — becomes load-bearing here: since a client can
call `/approve` on any `thread_id` at any time (one that never started,
one that already finished, one being approved twice), `/approve` and
`/reject` both call `graph.get_state(config)` first to check "is this
thread actually paused waiting for me?" before ever calling
`Command(resume=...)`. `graph.invoke()`'s return value alone can't answer
that anymore, now that the interrupt and its resume live in two separate
requests instead of one call stack.

## Architecture

```
Client (curl / TestClient / browser)
      |  HTTP JSON (thread_id in every body)
      v
FastAPI app (stage19_fastapi_backend/main.py, uvicorn process)
      |  graph.invoke(...) / graph.get_state(...) / Command(resume=...)
      v
Compiled LangGraph `graph` (PlannerState — plan -> human_approval ->
      |                      research_subtask loop -> synthesize)
      |  checkpointer=PostgresSaver(pg_conn)
      v
PostgreSQL (docker-compose `postgres` service, host port 5433)
```

`thread_id` is the only piece of state a client carries between calls —
there's no server-side session store. Every route builds
`config = {"configurable": {"thread_id": request.thread_id}}` fresh from
the request body. The graph, the `psycopg` connection, and the
`PostgresSaver` are constructed once at module-import time (same as Stage
18) — one shared instance reused across every request for the life of the
uvicorn process.

### A full `/chat` -> `/approve` cycle

```
POST /chat    {"question": "...", "thread_id": "abc"}
  -> graph.invoke({"question": ...}, config) runs plan -> human_approval,
     which calls interrupt(...) and pauses.
  <- 200 {"status": "awaiting_approval", "subtasks": [...], "approval_prompt": "..."}

POST /approve {"thread_id": "abc"}
  -> graph.get_state(config) confirms state.next == ("human_approval",)
  -> graph.invoke(Command(resume="y"), config) runs
     research_subtask (looped over every subtask) -> synthesize -> END
  <- 200 {"status": "completed", "subtasks": [...], "results": [...], "final_answer": "..."}
```

Rejecting instead (`POST /reject {"thread_id": "abc"}`) resumes with
`Command(resume="n")`; `route_after_approval` sends this straight to `END`
with no research run — `results` comes back `[]` and `final_answer` `""`.

## Endpoints

| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/health` | — | `{"status": "ok", "database": "connected"}`, or `503` if Postgres is unreachable |
| POST | `/chat` | `{"question": str, "thread_id": str}` | `202`-style `200` with `status: "awaiting_approval"`, the plan, and the approval prompt |
| POST | `/approve` | `{"thread_id": str}` | `200` with `status: "completed"`, `results`, and `final_answer` |
| POST | `/reject` | `{"thread_id": str}` | `200` with `status: "rejected"`, empty `results`/`final_answer` |

`thread_id` is **required and client-supplied** on every endpoint that
needs it — it is never generated by the server. This matches how this
stage's test file uses fixed string thread_ids (`"test-approve"`, etc.),
the same convention Stage 17/18's own tests use.

### Status codes

| Scenario | Code |
|---|---|
| Success | `200` |
| Missing/malformed request body | `422` (automatic, via Pydantic) |
| `/approve` or `/reject` on an unknown `thread_id` | `404` |
| `/approve` or `/reject` on a thread not currently awaiting approval (never started past `plan`, already completed, or already rejected) | `409` |
| `/health` when Postgres is unreachable | `503` |
| Unexpected error inside `graph.invoke(...)` (LLM/tool/DB failure) | `500` |

Every `HTTPException`'s `detail` is a short, static, hand-written string —
never the raw exception text or a traceback. The real exception is printed
server-side for debugging. A global `@app.exception_handler(Exception)`
catches anything that escapes a route's own `try/except` as a
defense-in-depth net, also returning a generic `500` with no internals
leaked.

## Design decisions

- **Per-thread_id locking around `/chat`, `/approve`, and `/reject`.** A
  client that doesn't wait for `/chat`'s response before firing `/approve`
  on the same `thread_id` (or double-submits `/approve`) used to be able to
  race `graph.get_state()` against `/chat`'s still-in-flight
  `graph.invoke()`, reading whatever checkpoint happened to be latest at
  that instant. For a brand-new `thread_id` that's just an empty
  snapshot (`404`); for a reused `thread_id` with prior completed history,
  it's a **stale but real** checkpoint from an earlier run — producing a
  misleading `409 "not currently awaiting approval"` even though `/chat`
  goes on to pause correctly moments later. Reproduced directly: firing
  `/approve` ~100ms after starting `/chat` on a thread_id with prior
  history returned `409` in under a second, while `/chat` itself (LLM-bound)
  took several seconds and then correctly returned `"awaiting_approval"`.

  The fix is an in-process `dict[str, threading.Lock]` keyed by `thread_id`
  (`_thread_locks` / `_lock_for` / `_thread_lock`, just above the FastAPI
  app). Each of `/chat`, `/approve`, and `/reject` holds that thread_id's
  lock for its *entire* body — from before the first `graph.get_state()`/
  `graph.invoke()` call to after the response is built — via a
  `try/finally`-backed context manager, so a second request for the same
  `thread_id` blocks until the first has fully committed its checkpoint,
  then reads fresh state instead of a stale one. A duplicate simultaneous
  `/approve` now resolves deterministically too: whichever request
  acquires the lock first resumes and completes (`200`); the other, once
  it acquires the now-free lock, correctly sees the thread already reached
  `END` and returns `409` — the same code as before, but now a legitimate
  answer instead of a race artifact. `THREAD_LOCK_TIMEOUT_SECONDS` (120s)
  bounds the wait, reusing `409` for a timed-out acquisition rather than
  introducing a new status code.

  **Scoped to a single process on purpose**, matching how this stage is
  documented to run (`python main.py`, or `uvicorn --reload` with no
  `--workers`) — an in-process `threading.Lock` needs no new dependency
  and no new infrastructure, unlike a Postgres advisory lock (which would
  need its own dedicated, non-autocommit connection to hold correctly for
  a request's duration) or a distributed lock service. **Known limitation:**
  if this stage is ever run with multiple worker processes or across
  multiple machines, each process gets its own lock registry and the race
  reopens across process boundaries — `pg_advisory_lock`/
  `pg_try_advisory_lock` (keyed by `hashtext(thread_id)`, on a dedicated
  connection) would be the correct fix at that point, not implemented here.
  The lock registry (`_thread_locks`) also grows by one small `Lock` object
  per distinct `thread_id` ever seen and is never pruned — an accepted
  tradeoff for a learning project, not a concern at this scale.
- **Sync route handlers (`def`, not `async def`).** FastAPI/Starlette
  automatically runs sync `def` routes in a worker threadpool, which is
  exactly what lets a blocking call stack (`graph.invoke` → sync OpenAI
  calls → sync `psycopg` queries) run without blocking the event loop —
  no `AsyncPostgresSaver`, no `await`, no new concepts, consistent with
  Stage 18's own sync-only decision.
- **Known limitation, not fixed here: a single shared `psycopg`
  connection.** `pg_conn` is one connection (not a pool), constructed once
  at module scope — same as Stage 18. Concurrent requests landing in
  different threadpool threads will contend for that one connection,
  effectively serializing concurrent graph calls rather than running them
  in true parallel. Fixing this (a `psycopg_pool.ConnectionPool`,
  per-request connections, or `AsyncPostgresSaver`) is out of scope for
  this stage.
- **`thread_id` kept client-supplied and required, not server-generated.**
  Matches the endpoint spec this stage was built against, and the existing
  test-file convention (Stage 17/18) of fixed string thread_ids rather
  than a fresh `uuid4()` per call.
- **`httpx` needed no new `requirements.txt` line.** `fastapi.testclient.
  TestClient` needs `httpx`, which is already installed transitively (via
  `openai`/`langchain-openai`/`langgraph-sdk`) — confirmed with
  `pip show httpx` before relying on it, not assumed.
- **`verify_persistence_api.py` uses `TestClient` in both phases, not a
  real socket.** `TestClient` talks to the ASGI `app` object in-process
  rather than over a real socket, but since each `python
  verify_persistence_api.py [...]` invocation is its own OS process with
  its own fresh import of `main.py`, the "fresh app/graph bound to the
  same Postgres DB" property this script is meant to demonstrate still
  genuinely holds. A real `uvicorn` server plus a `requests`-based script
  would exercise a real socket too, but wasn't implemented, to avoid
  adding a second HTTP client dependency for a demo script.
- **`GET /health` checks Postgres reachability, not just process
  liveness.** A plain `{"status": "ok"}` with no DB check would pass even
  if Postgres were down — the actual dependency worth verifying.

## How to run

Start Postgres (from the repo root, if not already running):

```
docker compose up -d
```

Install dependencies (adds `fastapi`/`uvicorn` to the existing set):

```
.venv\Scripts\activate
pip install -r requirements.txt
```

Run the API:

```
python stage19_fastapi_backend/main.py
```

or, for dev auto-reload (run from the repo root):

```
uvicorn stage19_fastapi_backend.main:app --reload --port 8000
```

## Running the tests

```
python stage19_fastapi_backend/test_fastapi_backend.py
```

Covers, all through `fastapi.testclient.TestClient` (no running server
needed): `/health`; a normal `/chat` producing a plan; two different
questions run back-to-back on the *same* `thread_id` (approve the first,
reject the second) without leaking the first's `final_answer`; a full
approve cycle producing a `final_answer`; a full reject cycle producing
none; three concurrency checks (`/approve` racing an in-flight `/chat` no
longer misfires with a stale-read `409`; a duplicate simultaneous
`/approve` resolves to exactly one `200` and one legitimate `409`, with
research running only once; two concurrent `/chat` calls on the same
thread_id don't corrupt the checkpoint chain); and the `404`/`409`/`422`
error cases.

## Verifying persistence across a restart

```
python stage19_fastapi_backend/verify_persistence_api.py
```

Sends a `POST /chat`, prints the plan and approval prompt, then exits
**without** approving — simulating a crash mid-decision. Optionally
restart the container too:

```
docker compose restart postgres
```

Then, in a brand-new process:

```
python stage19_fastapi_backend/verify_persistence_api.py --check
```

This calls `graph.get_state(config)` directly first (no HTTP, proving the
plan survived independent of any route), then sends `POST /approve`
through a freshly-built `TestClient` bound to a freshly-imported `app` —
proving a FastAPI app constructed in a brand-new process can resume a
thread it never itself started.

## What changed compared with Stage 18

| | Stage 18 | Stage 19 |
|---|---|---|
| Entrypoint | REPL `main()`, blocking `input()` | FastAPI `app` + `uvicorn.run(...)` |
| Interaction model | One process, blocking on `input()` for approval | Stateless HTTP requests keyed by client-supplied `thread_id` |
| Interrupt/resume | Same call stack (`run_until_settled`'s `while` loop) | Two separate requests (`/chat` then `/approve` or `/reject`) |
| Validating a resume | Implicit — `"__interrupt__" in result` from the same `invoke()` call | Explicit — `graph.get_state(config).next` checked before every `/approve`/`/reject` |
| Graph logic (nodes, edges, prompts, tools) | — | Byte-identical to Stage 18 |
| New infrastructure | — | None — reuses the existing `docker-compose.yml` Postgres service |
| New dependencies | — | `fastapi`, `uvicorn` |

Stage 18 proved a checkpointer is a pluggable backend behind
`compile(checkpointer=...)`. Stage 19 proves the graph itself is just as
indifferent to *how* it's called: a REPL loop, a test script, and now a
FastAPI route handler are all just callers of `graph.invoke(...)` —
nothing inside the graph had to change to support any of them.
